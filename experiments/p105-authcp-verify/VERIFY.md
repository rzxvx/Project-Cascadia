# Offline AuthCPAID mathematical verifier

This source-only host component closes a specific software gap: packet parsing
can copy a corrupt signature without detecting corruption. `authcp_verify.py`
performs real public-key verification. It does **not** trust the supplied key,
verify an accessory certificate chain, establish accessory identity, provide a
physical request fence, or authorize authentication/current/VBUS/USB role. There
is no bus/IRQ/kernel registration, signing function, private-key loader, network
client, or automatic invocation by the boot/build path.

## Actual source contracts and supported profiles

Existing original-instruction proof `experiments/p105-authcp-aid/emulate-iap-verify13.py`
executes pinned official 13G36 IAPAuthentication method `0x31a0e870` with a bounded
6000-instruction budget and verifies the actual imported API stubs. The cache
SHA256 is `4f5b5d73244c53fd0bdc5b8012106b10d0dd7607cc850bf7c8f9e9ef3a3f733b`.
CF objects, certificate parsing, optional-anchor once state, and Security APIs
are synthetic in that original-control-flow experiment. The new component uses
real cryptography independently, with synthetic keys; it does not turn those
mocked original trust calls into real trust validation.

| Source version | Original RawVerify arguments | Implemented mathematical profile |
| --- | --- | --- |
| 2 | padding `0x8002`, nonce20, signature128 | RSA1024 PKCS1-v1.5, SHA1 DigestInfo, exactly20 bytes supplied as the digest |
| 3 | padding `0x4000`, nonce32, signature64 | Explicitly supported P-256 profile; raw32-byte big-endian `r` followed by raw32-byte big-endian `s`, over exactly32 supplied digest bytes |

Original random nonce producer `GetRandomDigest` at `0x31a0fbbc` calls
`arc4random_buf`; the audited daemon caller selects20/32 bytes. Verification
passes these bytes unchanged. Hashing them a second time changes the operation.
For version3 the helper uses `ECDSA(Prehashed(SHA256))` to express the backend's
32-byte digest contract; this introduces **no hash computation** and makes no
claim that the random nonce was generated by SHA256.

The modern primary Apple [SecKey API definitions](https://github.com/apple-oss-distributions/Security/blob/db15acbe6a7f257a859ad9a3bb86097bfe0679d9/keychain/headers/SecKey.h)
identify `0x8002` as PKCS1/SHA1 and `0x4000` as raw big-endian ECDSA `r,s`, and
describe RawVerify's input as digest bytes. These API definitions explain the
observed numeric contract; they do not establish matching13G36 iAP certificate
policy. The [cryptography41.0.7 prehash API](https://cryptography.io/en/41.0.7/hazmat/primitives/asymmetric/utils/)
supports verification without a second hash. The independent public-key-only
known-answer test uses [RFC4754 section8.1](https://www.rfc-editor.org/rfc/rfc4754.txt)
public coordinates, digest and signature; its private/ephemeral key values are
not copied into this package. RFC4754 qualifies curve/scalar and encoding math,
not Apple's accessory protocol or trust policy.

`inspect_source.py` reads a caller-supplied, SHA-pinned complete official cache
and emits only embedded certificate algorithm/curve/length/fingerprint metadata.
Two embedded RSA public CA artifacts have2048-bit keys and BasicConstraints CA;
a third named accessory-certification artifact has a256-bit secp256r1 key but
no BasicConstraints extension. These are **not accessory leaf keys**. The last
artifact's curve is useful supporting context, not proof that every accessory
leaf is P-256, nor proof that it is the active version3 trust anchor. Consequently
P-256 is an explicit supported helper profile; other256-bit curves are rejected
rather than claimed equivalent to native policy. Native anchor initialization
and exact leaf policy remain separate work.

## Verification result and trust boundary

The frozen result contains `signature_valid`, scheme and public-key fingerprint.
A certificate input additionally yields its fingerprint. These identify input
bytes only; they do not pin a trusted accessory. On every path,
`certificate_chain_trusted=null`, `accessory_identity_verified=null`, and
`authorization_granted=false`. CLI exit0 means mathematical verification only.
Even an expired, self-signed synthetic leaf can supply the correct public key
and produce a mathematically valid result; the regression explicitly ensures it
still grants nothing.

The source native verifier first creates `SecPolicyCreateiAP`, evaluates a chain
with source-supplied anchors, accepts only API success plus trust result4, obtains
`SecTrustCopyPublicKey`, and then verifies the nonce signature. Generic TLS trust
or a matching public-key fingerprint cannot replace that pipeline. Exact13G36
anchors/extensions/leaf policy, pinned accessory identity, unpredictable fresh
nonce ownership, transcript association, and transport/IRQ drain must be qualified
before any authorization integration. This verifier detects tested substituted
chunks; it cannot identify the physical source of a frame, prevent replay when
nonce material is reused, or cancel chip-side pending operations.

Inputs are bounded immutable bytes. DER is a single definite minimally encoded
outer sequence; SPKI must round-trip to identical canonical bytes. RSA1024 and
P-256 key types/sizes are checked. Raw ECDSA scalars must lie strictly within the
curve order. No low-S restriction is invented: the native raw API supplies no
such observed policy, and both equivalent mathematical signatures are accepted.
The CLI reads only bounded regular files, rejects symlinks/FIFOs, and outputs no
nonce, signature, certificate or key bytes.

## Tests and dependency

The committed suite was independently repeated in an isolated copy-on-write
image with Python3.10.12, cryptography41.0.7 and its actual OpenSSL3.1.4 backend
(Python's separate stdlib ssl reports OpenSSL3.0.2). These are distinct library
versions; the stdlib version does not identify the verification backend.
`requirements.txt` pins
cryptography41.0.7; ordinary wheel dependency resolution may also need cffi and
pycparser. No package is installed by these scripts. The existing Cascadia image
currently lacks cryptography; do not treat that missing library as a skipped test
or install it automatically on the production host. Parent may construct a
separate verified build image for a reproducible suite. The repeated suite used
official binary wheels for cryptography41.0.7, cffi1.17.1 and pycparser2.22,
each SHA256-checked against PyPI release metadata, with no production-host
installation or modification to the original Cascadia image.

```
python3 test_authcp_verify.py
python3 test_pipeline_crypto.py --source-root /PATH/TO/CASCADIA
python3 inspect_source.py /PATH/TO/OFFICIAL/dyld_shared_cache_armv7
```

Eleven real-crypto test groups cover both profiles,244 individual signature/nonce
byte-corruption checks, wrong keys, accidental double hashing, wrong curves/key
sizes/versions, DER and raw-signature encoding, scalar bounds, equivalent ECDSA
signatures, untrusted expired synthetic certificates, CLI size/regular-file
limits, the independent RFC public known-answer vector, and direct RSA public-exponent
recovery of the PKCS1 SHA1 DigestInfo/non-rehashed input. The latter uses
[RFC8017 section9.2](https://www.rfc-editor.org/rfc/rfc8017.txt) encoding and
Python integer arithmetic independently of the signature-verification API. Private test keys are
generated and used only in memory, never written or printed. The negative loader
test creates a private-key DER buffer only in memory to prove that the production
public-key loader rejects it.

The coupled test compiles entire unchanged, SHA-pinned actual Linux-C transport
and parser sources under ASan/UBSan, with bounded fake regmap/lease providers.
The same source-derived32/32 frame templates are used for both versions. Tests
replace only synthetic signature payload bytes with real in-memory signatures.
Exact signatures reconstruct and verify. Repeating the first prior31-byte payload
under a newer unique request causes the actual parser to complete an UNVERIFIED
signature; the real verifier rejects it for both versions. This is a constructed
software counterexample, not an observed electrical late reply. Test outputs
contain only semantic outcomes/source hashes. Whole-C source is reused; no
handwritten production-function copies or Apple binary/private-key fixtures.

No new kernel code requires ARM compilation. Existing unchanged Linux-C components
were already compiled against real6.12 ARM headers in their separate groups;
this group adds a host Python verifier and sanitizer composition test only.
